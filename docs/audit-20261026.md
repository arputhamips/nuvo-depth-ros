# General-purpose driver audit — 26 October 2026

The ROS adapter is independent of Nuvo Base. Its measurement topics can be used
by any ROS 2 Jazzy application that accepts the documented message types, units,
frames and QoS. Camera acquisition still requires a compatible native Nuvo Depth
source. This audit covers source inspection and Linux amd64 tests under WSL2,
including a rebuilt Docker image. It does not qualify physical Pi/camera operation.

## Boundary review

| Area | Finding |
|---|---|
| Robot dependencies | No Nuvo Base package dependency, motor control, odometry, navigation configuration, robot dimensions, mounting transform or hard-coded robot endpoint in the driver |
| ROS interface | Standard Image, CameraInfo, PointCloud2, DisparityImage and DiagnosticArray messages; custom FrameMetadata only adds capture/calibration/time provenance |
| Topic consumers | Standard-message subscribers can obtain measurements without subscribing to FrameMetadata |
| Names and frames | Relative measurement topics respect namespaces and remaps; frame IDs are explicit parameters; the driver supplies no robot TF |
| Camera ownership | Native Nuvo Depth owns exposure, matching and calibration; local acquisition requests products; HTTPS creates a session and subscription without configuration writes |
| Calibration | Hash, authority and matching-grid geometry are retained; provisional output needs explicit opt-in; there is no implicit recalibration or authority promotion |
| Optional XYZ | Generated in this adapter only when enabled and subscribed; invalid samples remain NaN |
| SDK provenance | Exported files verify against their manifest and the canonical native worktree at `b653f06d35c4fcac7b966a3f02622eb0d58e4ec6`; no vendor files were edited |
| Distribution | Nuvo-authored files declare GPL-3.0-or-later; corrected the root NOTICE's copied references to gateway, installer, web console and fonts absent from this repository |
| Release discipline | Added regression checks to the existing artifact-producing CI workflow; no tags, release, publication or manual ARM64 build was initiated |

The Nuvo acquisition protocol and metadata are camera-specific. They are not
robot-specific application logic. The adapter does not depend on a closed
Nuvo Base runtime or require a downstream project to use Nuvo's custom message.

## Changes from this audit

- Fixed the installed C++ interface: previously `find_package(nuvo_camera)`
  provided no linkable target despite installing public headers. It now exports
  `nuvo_camera::nuvo_camera_component`, headers and transitive dependencies.
  An external consumer reproduces the old failure and passes with the fix.
- Declared direct `std_msgs`, `rcl_interfaces` and launch dependencies explicitly.
- Added the `name` argument to camera and inspection launch files. Exact
  node-scoped YAML now has a tested path with custom node names and namespaces.
- Added `NUVO_NAMESPACE` and `NUVO_CONFIG` Compose settings so deployments can
  choose their namespace and YAML without editing the shared service definition.
- Made the default camera/replay right optical frame use the same `nuvo_front`
  prefix as the left frame. Custom frame IDs remain independent of namespaces.
- Corrected the first-publication log to say measurement, since image-only
  subscriptions can publish without depth.
- Added the [robot integration walkthrough](using-in-robot.md): connection
  choices, configuration, standard topic consumption, QoS, remapping, RViz,
  components, multiple cameras and the robot's TF responsibilities.
- Added installed-consumer and two-camera standalone/component regression checks
  to routine CI.

## Native checkout distinction and limits

At audit time, `Documents/Nuvo Depth` was on `2165aee` with pre-existing local
changes. Its local `sdk/cpp` tree predates the reviewed SDK snapshot here and
lacks the newer measurement tests. The separate canonical native worktree on
`codex/universal-depth-contracts` at `b653f06` matches every exported SDK file.
Refreshing from the older working directory would discard newer validation and
API fields. No native checkout or vendor snapshot was changed by this audit.

The older checkout's `geometry.nuv` serializer fixture deliberately contains a
stereo-configuration rejection and arbitrary, inconsistent depth/disparity
values. An attempted positive replay test correctly produced no measurements
and reported `producer stereo configuration rejected`. This is not evidence of
a runtime camera failure. The valid canonical fixture from `b653f06` was then
built against the current checkout's native libraries and passed unchanged
through SDK decoding and ROS DDS. The relevant serializer/product sources were
also checked equal between those two native revisions.

Public beta 8 still needs the documented hash/grid-matched geometry override;
optional products require their producer metadata. There is no released minimum
native version covering all capabilities. Use a reviewed native revision and
preserve its calibration. ROS 1, other ROS 2 distributions, compressed image
transports and RGB-aligned depth are outside the tested interface. Metric
accuracy, camera throughput, latency and endurance still require real hardware
qualification.
